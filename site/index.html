YASS! Yet Another Spec System.

YASS is the bridge between your project management system and your code: the missing link for your software factory. It keeps the plan, progress and decisions for each change in plain files next to the code, so people and agents can plan and build together.

Install Why YASS GitHub

Install

Agent Prompt

Paste this into your coding agent, from inside your repo. It asks before each step, and you can read the steps first.

Install YASS and set it up in this repo by following https://raw.githubusercontent.com/donjaime/yass/main/INSTALL.md. Ask me before changing anything.

Terminal

Install the binary (read the script, or install from a release), then set up your repo from inside it.

curl -fsSL https://raw.githubusercontent.com/donjaime/yass/main/install.sh | bash
yass init

From Source

With Go 1.24 or later, then set up your repo from inside it.

go install github.com/donjaime/yass/cmd/yass@latest
yass init

Describe the change, not the whole system.

Your code, docs and READMEs are the source of truth for what exists, and the memory your agents already read. YASS doesn't write it down a second time. It specs only what needs to change, tracks progress as it's built, and keeps it all next to the code, in plain markdown that agents and humans both read. It's lightweight project management for people and coding agents.

Spec-driven, without a second spec

Agents build from a written spec, but only for the change. There's no second description of your system to drift out of date. When a change is done, it moves to the archive, and the archive tells the story of how the product got here.

Ceremony scales with scope

A bug fix is one file. A new system gets a PRD, a plan, the hard-to-undo calls, and PR-sized pieces, all in the same folder.

Decisions you can find

Who decided what, and why, is written down as the work happens. Plan changes get their own commits, so they can be reviewed apart from the code.

A change is a folder.

Each change worth reviewing gets a dated folder. Progress, decisions and a log travel in it, in the same commits as the code they describe. Unambiguous work, like a typo fix or a mechanical cleanup, skips it: that's just a good pull request.

yass/
├── changes/                       active work
│   ├── 2026-10-02-fix-double-tap-save/
│   │   └── change.md              small: goal, acceptance, steps, decisions, log
│   └── 2026-09-14-offline-sync/
│       ├── change.md              large: goal, decisions, log…
│       ├── prd.md                 …why and what
│       ├── plan.md                …how, and acceptance criteria
│       ├── design.md              …the hard-to-undo calls (optional)
│       └── 2026-09-16-offline-queue/  …and PR-sized pieces
└── archive/                       finished changes, as they were

That's the whole system: no database, no server, no integrations to set up. One small CLI, seven playbooks your agent follows, and an optional git hook. It fits the workflow you already have: plans and progress travel in the same commits and pull requests as the code, and YASS never commits for you.

You talk to your agent.

The playbooks are skills your agent already knows how to follow. You don't learn a process; you ask.

You sayPlaybookWhat happens
“Let's build offline sync”yass-shapea conversation that ends in a PRD you approve
“Plan it”yass-planapproach, acceptance criteria and PR-sized pieces; nothing gets built yet
“Fix the double-tap crash” or “Keep going”yass-workbuilds against the acceptance criteria, ticking boxes and logging as it goes, resuming from the last Next:
“Where are we?”yass-statusprogress, blockers, recent decisions, what's ready to archive
“Why did we pick SQLite?”yass-logthe decision, who made it and when, with the code that carried it out
“Connect our Trello board” or “Connect Jira”yass-initthe repo set up, and your project management system connected: a Trello board adopted, or your team's workflow for the others written down once
“Update YASS”yass-updatea verified newer binary, then the repo upgraded, asking before it downloads

The playbooks are Agent Skills, read natively by Codex, OpenCode and pi, and by Claude Code with --claude. Any agent that can read files and run a shell command can follow the rules. A plan from your harness’s plan mode becomes a change.

For building software factories.

From a solo developer to a large organization with many teams, YASS fits the agentic product development life cycle you're building. Work flows in from the project management system you already run (Jira, Linear, GitHub Issues, Trello…), agents plan and build it next to the code, and the board follows along.

  1. Ideas, Will Do
    On the board The backlog, and what your team picks next.
    In the repo Nothing yet.
  2. Planning
    On the board The card moves when shaping starts, and links the plan for review.
    In the repo A change folder with the why, the what and the how, reviewed in its own pull request.
  3. Implementing
    On the board The card moves when building starts, and links each pull request.
    In the repo The code, with progress, decisions and a log in the same commits.
  4. Done
    On the board The card moves when the change is archived.
    In the repo The change moves to archive/: the record of what changed, and why.

Your agent moves the card, through the connector or CLI it already has; everything finer stays in the files, so the board stays readable. YASS and your project management system
