## Changes (YASS)
Planned work lives in the yass folder's `changes/`, one dated folder per change: `yass/` in the repo, or wherever `yass.yaml` points (`yass root` prints it; see its README.md). CLI: `yass`, on your PATH. Playbooks: the `yass-*` skills, in `.agents/skills/` or your user skills folder. This section is the summary; the playbook that fits the task has the detail.
- Not every pull request needs a change. When the intent of work that has none is unambiguous and fits in a pull request's description (a trivial fix, a mechanical cleanup, a one-off), skip YASS and open one good pull request; trivial work needs no question. When it deserves discussion, review or approval, ask whether to start a change (`yass-work` for small, `yass-shape` for large), or to shape it with `yass-shape` and land plain pull requests from the brief you agree on. Unattended, stop and ask rather than build without one, unless you were told when dispatched not to stop for that.
- At the start of work, run `yass me`: who you're working for in this clone and, on a repo shared by teams, which yass folders are theirs. Change it only with `yass me`, never by opening its file.
- Work only on the change you're pointed at, unless you've been put in charge of choosing (`yass-work`). `yass status` shows what's in flight; `not started` means planned, and its plan may still need approval. Resume from the last **Next:** in its Log, and keep its boxes (`[/]` started, `[x]` verified), `## Log` and `## Decisions` (`- <decision> - <why> (<who>, <YYYY-MM-DD>)`) current alongside the code.
- Intent (`prd.md`, `design.md`, plan text, a Goal, acceptance criteria, including dropping one with `[-]`) never changes in the same commit as code (with squash merges, the same pull request), so decisions can be reviewed apart from execution. If the plan is wrong mid-build, put the fix on its own branch underneath the code (see `yass-work`), or stop and say so.
- Don't commit, branch, rebase, push or open a pull request unless you've been given that latitude; otherwise show the human the git commands.
- Write pull requests and commits for people: a plain-language title, the intent first, then what changed and how it was checked, with YASS's codes last in a collapsed "YASS tracking" block.
- Finished means every box is checked; then `yass archive <change>`, as the last commit of the pull request that ticks the last box. Never edit the archive (`archive/` in the yass folder): follow-up work is a new change with `follows: <archived folder>`.
- If `yass root` is outside this repo, plans and code are committed separately: see `plans-elsewhere.md` in the `yass-work` playbook's folder.
- When a yass folder has a tracker (`tracker:` in its `settings.yaml`), update it as the Trello workflow says (`trello.md` in the `yass-init` playbook's folder), or, for another tracker, as the folder's `team.md` says under `## Project management`.
- Also: `yass-init` sets YASS up here or connects a tracker; `yass-update` when `yass status` notes that the `yass` binary and this repo's YASS files are out of step; `yass-shape` or `yass-plan` turn a plan from plan mode into a change.
